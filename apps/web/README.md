# apps/web — Campo 2.0 (frontend)

Next.js (App Router) + TypeScript estricto + Tailwind v4 + Zustand + React Three Fiber/drei. PWA instalable.

## Arranque

```bash
npm install
npm run dev          # http://localhost:3000 — modo DEMO si no hay NEXT_PUBLIC_WS_URL
npm run lint && npm run typecheck && npm test && npm run build
npm run e2e          # next build + next start + Playwright (escritorio y móvil) → e2e/screenshots/
npm run e2e:admin    # e2e de /admin en modo demo (1440x900 y 390x844) → e2e/screenshots/admin-*.png
npm run e2e:models   # e2e del catálogo vivo y los modelos 3D (demo, 1440x900 y 390x844) → e2e/screenshots/models-*.png
npm run e2e:modules  # e2e de clientes y módulos: cada módulo, «Ver como», plantilla maestra, alto contraste y modo pared → e2e/screenshots/modules-*.png
```
`SKIP_BUILD=1` reutiliza el build en los e2e (puertos 3217–3220). Comparten la carpeta de build: para lanzar dos a la vez, dale a cada uno su carpeta con `NEXT_DIST_DIR=.next-xyz` (se usa también en `next build`).

## Variables (se incrustan en build)

| Variable | Uso |
|---|---|
| `NEXT_PUBLIC_WS_URL` | URL del WebSocket (`wss://host/ws`); se le añade `?plant=&token=`. Si falta → modo demo |
| `NEXT_PUBLIC_API_URL` | Base REST (`''` = mismo origen): login, alarmas, y toda la administración (`/api/me`, `/api/plants*`, `/api/users*`, `/api/alarm-rules*`, `/api/audit`, `/api/me/password`) |
| `NEXT_PUBLIC_PLANT` | Planta preferida al entrar si el usuario no tiene una recordada (def. `demo`) |
| `NEXT_PUBLIC_MOCK` | `1`/`0` fuerza demo / real. En demo tanto el stream como la API de administración son simulados |

## Arquitectura

- `src/lib/` utilidades puras (backoff, batcher rAF, parseo de mensajes, estados, métricas).
- `src/store/live-store.ts` (`useLiveStore`: activos, alarmas, conexión) y `history.ts` (buffers circulares fuera de React).
- `src/live/` cliente WS con reconexión (backoff exponencial + jitter), simulador de la planta demo (`ServerMessage` idénticos a los del WS) y arranque.
- `src/scene/` gemelo 3D (carga dinámica, sólo escritorio o móvil bajo demanda): el 3D lee con `useLiveStore.subscribe` y refs, interpola en `useFrame`; `frameloop="demand"` a 30 fps; calidad baja automática con render por software.
- `src/components/` UI: plantilla maestra (`shell/`), pantallas de módulo (`modules/`), modo pared (`wall/`), y el 3D de siempre (`DesktopShell`/`MobileShell`, módulo `view3d`).
- `src/lib/modules/` dominio puro y testeado: navegación por módulos, escala, estado/«cerca del límite», tendencia, KPIs, extras de tarjeta, resumen.
- `src/lib/admin/` capa de API de administración: `AdminApi` (interfaz tipada, `types.ts`), `HttpAdminApi` (fetch + Bearer; `errors.ts` convierte 400/401/403/404/409/red en `AdminApiError` con mensajes en español, sin trazas; un 401 limpia el token y vuelve a `/login`), `MockAdminApi` (en memoria, sembrada desde `src/lib/demo-seed.ts` con los dos clientes demo —`campos-demo`/planta `demo` y `cliente-tanques`/planta `tanques`—, reglas coherentes con `DEMO_LIMITS`, 9 usuarios y auditoría; hace cumplir igual que la API real el aislamiento por cliente, los módulos contratados, los 400/403/404/409, `affectedRules`, "último admin" por cliente y la auditoría de cada cambio), `access.ts` (guardas por rol), `validation.ts` (formularios, coherente con los DTO del servidor). `getAdminApi()` elige mock o HTTP igual que el stream (`config.mock`).
- `src/store/session-store.ts` (usuario + plantas, con caché local para abrir sin red), `plant-store.ts` (plantas y planta activa, recordada en `localStorage` `campo.plant`), `toast-store.ts` (avisos `aria-live`).
- `src/components/admin/` pantallas de `/admin` (Usuarios, Plantas y activos, Reglas, Auditoría, Mi cuenta), diálogos accesibles (`Modal`/`ConfirmDialog`: `role=dialog|alertdialog`, foco atrapado, Esc, foco devuelto) y campos de formulario.
- `public/sw.js` service worker (shell offline, caché de estáticos); iconos generados con `node scripts/gen-icons.mjs`.

## Plantas y administración

- **Selector de planta** en la cabecera (agrupado por cliente para `platform_admin`) (de `GET /api/plants`; no aparece si sólo hay una). Cambiarla para y vuelve a arrancar el stream (`startLive(plant)`): se cierra el WebSocket, se limpia el estado vivo, el histórico y la selección, y se conecta a `/ws?plant=<nueva>`. Un usuario sin plantas ve «Sin plantas asignadas». Las plantas distintas de `demo` no tienen layout 3D propio: sin ids conocidos se colocan en cuadrícula centrada y sin tuberías; con mezcla, los desconocidos van a la fila trasera. En modo demo, una planta creada simula valores suaves para los activos de su catálogo mock.
- **`/admin`** (barra lateral en escritorio, pestañas inferiores en móvil; tablas → tarjetas; textos en voseo rioplatense). Navegación por rol (`lib/admin/access.ts`): `platform_admin` (personal de Campos Ingeniería) ve **Clientes** y todo lo demás; `admin` de cliente: Usuarios, Plantas y activos, Reglas de alarma, Auditoría, Mi cuenta (siempre dentro de su cliente); `engineer`: Plantas y activos, Reglas, Mi cuenta; `operator`/`viewer`: Mi cuenta. El acceso se protege en cliente (403 amigable) pero la API es la autoridad.
- **Clientes y módulos** (`docs/architecture.md` §11). `/admin/orgs` (sólo `platform_admin`): lista (nombre, id, módulos como chips, nº de plantas y usuarios, estado; tarjetas en móvil), alta/edición con **interruptores de módulos** (descripción tomada de `MODULES`), id inmutable (validado con `ID_PATTERN`), activar/desactivar con confirmación que avisa que corta el acceso de todos sus usuarios, borrado escribiendo el id (muestra el 409 con las plantas/usuarios que lo bloquean) y «Crear administrador del cliente» (correo + contraseña ≥ 12 con indicador de fortaleza). `/admin/orgs/[org]`: módulos activos, plantas y usuarios del cliente, con enlaces filtrados (`/admin/users?org=`, `/admin/plants?org=`, `/admin/audit?org=`). En Usuarios, Plantas y Auditoría el `platform_admin` ve la columna/filtro **Cliente** y elige cliente al crear; un admin de cliente nunca ve opciones de otros clientes ni puede otorgar `platform_admin`.
- **Activos por módulo**: el selector de **tipo** muestra el nombre de `ASSET_KINDS` y deja elegir sólo los de módulos contratados (el resto figura «no contratado»; un 403 `module_disabled` se muestra como «Este módulo no está contratado, pedíselo a Campos Ingeniería»). Campos de dominio opcionales: `capacityM3` (tanques), `contractedKw` (energía) y `scale` (mín/máx por métrica), validados y sincronizados con el JSON avanzado sin pisar claves manuales. **Reglas de alarma**: las métricas sugeridas salen del tipo de los activos que abarca el id o patrón (`ASSET_KINDS`/`METRICS`); `/admin/rules?plant=<id>&module=<id>` preselecciona la planta y filtra por los tipos del módulo. **Mi cuenta** muestra el cliente, los módulos contratados con su descripción y «Para sumar más módulos, contactá a Campos Ingeniería» (mailto al correo de `NEXT_PUBLIC_CONTACT_EMAIL`, por defecto `info@camposingenieria.ar`).
- **Modo demo**: los datos de administración viven en memoria (se reinician al recargar). La identidad sale de `getDemoOrgId()` (`localStorage` `campo.demoOrg`; `platform` = `platform_admin` sin cliente) y de `campo.demoRole`; en *Mi cuenta* se elige rol y cliente de la sesión demo. La contraseña inicial de los usuarios demo es `demo-password-123`. Pruebas: `npm test` (unitarios), `npm run e2e:admin`, `e2e:models` y `e2e:orgs` (clientes y módulos, escritorio y móvil).
- Supuestos de forma no fijados por el contrato (alinear con la API): filtro por cliente `?orgId=` en `GET /api/plants|users|audit`, `orgId` en el cuerpo de `POST /api/plants|users`, `POST /api/orgs/:id/admins` → `ManagedUser`, y entradas de auditoría con `orgId`. Un cliente con usuarios no se puede borrar mientras no exista un borrado de usuarios.
- Respuestas no especificadas en `docs/architecture.md` que el cliente asume (confirmadas con la API): `POST /api/users/:id/revoke` → `ManagedUser`; `DELETE /api/plants/:plant` → `{deleted:true}`; `DELETE` de activo → `{deleted:true, affectedRules:n}`; `POST /api/me/password` → `{accessToken}` (se guarda). Desactivar o revocar sube la versión de token: el usuario afectado recibe 401 y vuelve a `/login`.
- Auditoría: `GET /api/audit?limit=50&before=<id>&actor=&action=`; «Cargar más» pide la página siguiente con `before` = id de la última entrada.

## Clientes y módulos (Fase 6, `docs/architecture.md` §11)

La plataforma se adapta a cada cliente: sólo se ve lo que contrató (`me.org.modules`). Sumar un módulo es activarlo y conectar los sensores; no hay código nuevo en la navegación.

- **Rutas**: `/` lleva al primer módulo activo (o a «Sin módulos contratados» con el contacto a Campos Ingeniería); `/m/[module]` (`tanks`, `climate`, `energy`, `gas`, `machines`, `flow`, `view3d`); `/alarmas` (todas las alarmas); `/pared` (modo pared). Un módulo no contratado, o inexistente, muestra «Este módulo no está contratado» también por URL. El 3D de siempre es el módulo `view3d` (en móvil el Canvas sigue siendo opt-in).
- **Plantilla maestra bloqueada** (`components/shell/MasterLayout.tsx`, ISA-101, `docs/ux-isa.md` §2.1): un único layout con **cabecera**, **barra de navegación** (lateral en escritorio con 2+ módulos; inferior en móvil, máx. 4 destinos: con más de 4 módulos, 3 + «Más») y **pie global de alarmas** (conteo de críticas/advertencias, las 3 más importantes con activo, valor y límite, y «Ver todas»), fijos en todas las pantallas. Con un solo módulo no hay barra de secciones. Las pantallas sólo aportan el contenido; la navegación sale únicamente de `me.org.modules` (más Alarmas, Modo pared, Administración y Mi cuenta del núcleo). `/pared` la oculta a propósito. Insignias por módulo: ámbar = activos cerca del límite, roja = alarma crítica.
- **Pantalla de módulo** (Nivel 2 ISA-101, `components/modules/`): pestañas **En vivo · Alarmas · Reglas**. En vivo = franja de resumen específica del módulo (`lib/modules/kpis.ts`), filtros «Todos (n)» / «Requieren atención (n)» y tarjetas (`ModuleCard`): estado (**En rango / Cerca del límite / Alarma / Sin datos / No catalogado**, siempre icono + texto + color), valor grande con unidad y decimales de `METRICS`, barra con la escala y marcas en los límites (y rombo en el setpoint si existe), tendencia y mini-curva, y pie con extras por tipo (`lib/modules/extras.ts`). Reglas enlaza a `/admin/rules?plant=&module=` (sólo admin/engineer/platform_admin).
- **Estado «Cerca del límite»** (`lib/modules/status.ts`, ISA-101): ámbar cuando el valor recorre el **90 %** de la distancia entre el setpoint y el límite de alarma. El setpoint sale de `metadata.setpoints[métrica]` o de la métrica `sp` de la telemetría (sólo la principal); sin setpoint la distancia se mide desde el mínimo de la escala (límites superiores) o su máximo (inferiores). Rojo = alarma activa. Un valor ya pasado del límite pero sin alarma todavía (retardo `forSeconds`) también se muestra «Cerca del límite».
- **Escala de la barra** (`lib/modules/scale.ts`): `metadata.scale[métrica]` tal cual; si no, la de `METRICS` ampliada para que quepan la potencia contratada y los umbrales de los límites (con 10 % de margen).
- **Límites** (`lib/limits.ts`): `GET /api/plants/:plant/limits` (en demo, `DEMO_LIMITS`); se guardan por activo en `useLiveStore` y se recargan junto al catálogo (`{type:"catalog"}` y reconexión).
- **Tendencia** (`lib/modules/trend.ts`): regresión lineal por mínimos cuadrados sobre los últimos 5 min del buffer circular (mín. 5 muestras y 20 s). «Estable» = menos del 3 % de la escala por hora (p. ej. 3 %/h en nivel, 1,8 °C/h en −10…50 °C). El caudal de llenado/vaciado de un tanque es la pendiente del nivel × capacidad (`metadata.capacityM3`).
- **Sin re-render por mensaje**: las tarjetas usan selectores finos por activo; los agregados (KPIs, insignias) salen de un derivado limitado a 1 Hz (`components/modules/derived.ts`).
- **Sesión y cliente**: `me.org` ({id,name,modules} o null para plataforma). En demo sale de `getDemoOrgId()` (`lib/demo-org.ts`); el menú de usuario trae **«Ver como»** (cliente con todos los módulos / sólo tanques / Campos Ingeniería) que cambia el cliente y recarga el estado (el rol demo sigue en Mi cuenta). El personal de plataforma ve los módulos del cliente dueño de la planta elegida (de `GET /api/orgs`, o `DEMO_ORGS`) y el selector de planta agrupa por cliente.
- **Modo pared** (`/pared`, `components/wall/`, lógica pura en `lib/wall.ts`): pantalla completa (Fullscreen API si se puede), sin menús, rotación automática entre los módulos con tarjetas (10/20/30 s; un toque pausa; la Vista 3D no rota), reloj, estado de conexión discreto, borde rojo grueso y franja en alarmas críticas, *wake lock* con degradación silenciosa, reconexión automática. Sale con Esc, al salir de pantalla completa o con un toque largo (700 ms). Funciona en vertical.
- **Alto contraste para luz solar** (`lib/theme.ts`, `components/ThemeToggle.tsx`): interruptor en el menú de usuario (y en la barra lateral / cabecera de escritorio); tema claro con tokens propios en `globals.css` (`html[data-theme='contrast']`), texto principal AAA (≥ 7:1), estados siempre con color + icono + texto. Se recuerda en `localStorage` (`campo.theme`) y se aplica antes de pintar. `src/app/tokens.test.ts` verifica los contrastes de ambos temas (en el oscuro se aclaró `--color-crit` de #f0563a a #f56a50 y `--color-bad` de #7f92a3 a #8fa1b1 para llegar a AA sobre todas las superficies; se añadieron `--color-calm`/`--color-calm-bar` para lo normal).
- **Simulación demo** (`live/seed-simulator.ts`, `live/mock-source.ts`): todos los activos de `DEMO_ASSETS` de `demo` y `tanques` generan telemetría realista (ciclos suaves, contadores monótonos, cambios de estado, excursiones hacia los límites de `DEMO_LIMITS` con sus alarmas). Tanques/bombas/válvulas de `demo` los mueve `PlantSimulator` a ritmo reducido (`speed` 0,2) para que caudales y tasas sean creíbles.
- **Identidad**: marca en cabecera/barra lateral/carga (`Brand.tsx`, `BrandLoader`), patrón de hexágonos de la marca (`HexPattern`, opacidad 4,5 %) en la cabecera de los módulos y el login, `loading.tsx`/`error.tsx`/`not-found.tsx` sobrios, textos en voseo rioplatense (`lib/voseo.test.ts` evita regresiones fuera de administración). Lo normal va en verde azulado atenuado; ámbar = atención, rojo = alarma.

## Catálogo vivo y modelos 3D (Fase 5, `docs/architecture.md` §10)

- **La lista y el 3D salen del catálogo**, no de la telemetría. `startLive(plant)` pide `GET /api/plants/:plant/assets` (vía `AdminApi.listAssets`, también en demo) y lo guarda en `useLiveStore` (`catalog`, `catalogReady`, `catalogError`); `assetIds` = catálogo ∪ telemetría, ordenado por tipo. `live/catalog-sync.ts` vuelve a pedirlo al recibir `{type:"catalog", plant}` por WebSocket (*debounce* 300 ms, una sola petición en vuelo, reintento con espera creciente si falla; también tras reconectar). Si el contenido no cambia no se tocan las referencias (nada se re-renderiza). En demo, `MockAdminApi.onCatalogChange` hace que el stream simulado emita ese mismo mensaje al editar activos o modelos.
- **Estados**: activo del catálogo sin telemetría → «Sin datos» (gris, icono de círculo discontinuo, sin valores) en la lista de escritorio, las tarjetas móviles, el panel de detalle y el 3D (tintado gris); activo con telemetría pero fuera del catálogo → etiqueta «No catalogado» (sólo con el catálogo ya cargado). Sin catálogo ni datos hay un estado vacío explicativo (cargando / error / catálogo vacío), no «Esperando datos…».
- **3D** (`src/scene/`): `SceneEntities` dibuja cada activo por su `type` (`tank`/`pump`/`valve` procedurales; `sensor` = mástil con cabezal) en `metadata.layout` (`x,z,y,rotY°,scale`), si falta en la posición manual de los ids de `demo` y si no en la cuadrícula automática (`resolvePlacements`, `layout.ts`). La cámara y el suelo se ajustan a los límites de la planta (`sceneBounds`/`fitView`). Los datos en vivo se leen por `SceneData` (suscripción transitoria; en la vista previa de administración es un origen vacío → «sin datos»).
- **Modelos GLB** (`src/scene/models/`): `model3dRef = "model:<uuid>"` → `AdminApi.downloadModel` (fetch + Bearer, 401 → `/login`) → `parseGlb` (`GLTFLoader.parse` sobre el `ArrayBuffer`; sin Draco/meshopt/KTX2; las URIs que no sean `blob:`/`data:` se neutralizan y el modelo se rechaza; límites de 10 MB, 200 000 vértices y 2 000 nodos; se descartan luces y cámaras del archivo). `ModelCache` comparte una sola descarga por id (peticiones en vuelo deduplicadas, máx. 2 simultáneas, errores no cacheados) y libera geometrías/materiales/texturas cuando el último activo lo suelta (3 s de gracia) o cambia de planta. Cada activo recibe un clon con materiales propios, se normaliza a una caja de **1 unidad de lado** (apoyada en y=0) y se multiplica por `layout.scale` (p. ej. 3,5 para un tanque). Convenciones `campo_level*` / `campo_rotor*` / `campo_gate*` y tinte por estado en `conventions.ts` (funciones puras). Mientras carga, o si falla (o si lo dibujado lanza un error), se usa el modelo procedural y el panel del activo muestra «Modelo no disponible».
- **Tuberías**: si algún activo declara `metadata.connectsTo`, se dibuja una tubería ortogonal por par (recortada por la huella de ambos) con partículas de flujo cuando el origen es una bomba con rpm>0 o una válvula con apertura>0; si ninguno lo declara, las tuberías manuales de `demo` (que se ocultan si se mueve un activo de demo con `layout`) o ninguna.
- **Administración** (`/admin/plants/[plant]`): formulario de activo con selector **Modelo 3D** (Procedural / modelos de la planta / «Subir nuevo…»), **Posición X, Z, Altura Y, Rotación, Escala** (rangos del contrato; admite coma decimal) y **Conectado a**; los campos y el JSON avanzado se mantienen sincronizados sin pisar otras claves de `metadata`, y los `warnings` de la API se muestran tras guardar. Sección **Modelos 3D** (lista con tamaño, fecha y nº de activos; subida con input accesible o arrastrando, validación de extensión y ≤ 10 MB en cliente, barra de progreso por XHR, errores 400/413 junto al control; borrado con confirmación y lista de activos del 409). **Vista previa 3D** de la planta (import dinámico; sola en escritorio, botón «Ver vista previa» en móvil).
- Un valor antiguo de `model3dRef` que no sea `model:<uuid>` (p. ej. `tank`) se trata como «sin modelo» y sólo se reenvía si el usuario no cambia ese campo (la API tolera reenviarlo igual).
- `MockAdminApi` (demo) implementa los modelos en memoria: valida la cabecera GLB, versión, longitud, extensiones, URIs externas y límites (400 `GLB no válido: …`, 413 `El modelo supera el límite de 10 MB`), deduplica por sha256 (200 vs 201), 409 con lista de activos al borrar un modelo en uso, `warnings` por `connectsTo` inexistentes (que no se guardan) y auditoría `model.upload`/`model.delete`.
